# コーディングルール

このファイルは、Codexが作業前に必ず読む必須ルールです。
詳しい理由や長い例ではなく、実装時に守ることだけを書く。
迷った場合は `docs/coding-reference.md` を確認する。

---

## 1. 作業前に必ず確認すること

- 修正前に、対象のHTML・SCSS・JavaScriptの構造を確認する。
- 実装前に、修正するファイルと修正方針を簡単に説明する。
- 既存デザイン、既存クラス名、既存の書き方を優先する。
- いきなり大きく作り替えず、必要な箇所だけ修正する。
- 不要なコード、不要なJavaScript、不要なアニメーションを追加しない。
- 依頼内容に関係ないコード、装飾、ライブラリ、クラスを追加しない。
- 迷った場合は、新しく追加せず既存の構成を優先する。

---

## 2. HTMLルール

- クラス名はBEMを基本にする。
- 基本形は `block__element` とする。
- 各セクションの中身は `__inner` で横幅を管理する。
- テキスト、カード、ボタンなどの中身は、基本的に `__inner` の中に入れる。
- 背景を画面いっぱいにしたい場合は、section側に背景を指定する。
- 画像を配置するだけの場合は、基本的に `div` で囲む。
- `figure` は、画像と `figcaption` をセットで扱う場合だけ使う。
- 装飾画像は `alt=""` にする。
- 内容を伝える画像には、意味が分かる `alt` を書く。
- 背景・装飾目的の画像は、HTMLの `img` ではなくCSSの `background-image` を使う。

---

## 3. SCSS基本ルール

- SCSSはネスト形式で書く。
- 既存のフォルダ構成に合わせる。
- 共通パーツは `object/component` に置く。
- ページ固有のセクションは `object/project` に置く。
- 全体の土台は `foundation` に置く。
- ヘッダー・フッターなどの大枠は `layout` に置く。
- SCSSはHTMLの並び順に合わせて書く。
- `__inner` は基本的に `max-width` で最大幅を決め、`margin: 0 auto;` で中央寄せし、`padding` で左右余白を確保する。
- 中央寄せを目的に、左右の `padding` を大きく指定しない。
- 中央寄せは `max-width` / `width` と `margin: 0 auto;` または `margin-inline: auto;` で行う。
- `padding` は中央寄せではなく、内側の余白として使う。
- section側は上下余白や背景を担当し、横幅管理は基本的に `__inner` で行う。
- 大きい画像・カード・コンテンツが入る場所では、左右paddingで無理に幅を調整しない。
- タグ名に直接スタイルを当てすぎず、基本はクラス指定で書く。
- 色は各SCSSファイルに直接書かず、必ず `var(--xxx)` を使う。
- 同じ要素に対して、PC用のサイズ・余白・配置を複数箇所で重複指定しない。

---

## 4. レスポンシブルール

- スマホファーストで書く。
- 通常のSCSSにはスマホ用のスタイルを書く。
- タブレット以上・PC以上の調整はmixinで書く。
- レスポンシブ指定は、対象クラスの中にまとめて書く。
- 別の場所にメディアクエリだけをまとめない。
- スマホ・タブレット・PCで崩れないように確認する。
- スマホ時に左右の余白がなくならないようにする。
- 画像ははみ出さないようにする。

使用するブレイクポイント:

- スマホのデザイン基準幅：375px
- `sp`：767px以下
- `tab`：768px以上
- `lt`：1024px以上
- `pc`：1440px以上

使用するmixin:

- `@include v.sp`：767px以下の例外的な調整のみ
- `@include v.tab`：768px以上
- `@include v.lt`：1024px以上
- `@include v.pc`：1440px以上

---

## 5. 可変サイズルール

- 画面幅に応じて自然に変化させたい値は `v.fluid()` を使う。
- 手書きの `clamp()` は原則使わない。
- `v.fluid()` は原則として4引数で書く。
- 引数は `v.fluid(最小サイズ, 最大サイズ, 最小画面幅, 最大画面幅)` とする。
- 可変値はpxベースで考える。
- min/maxの差が10px以下、またはvwの値が極端になる場合は固定値でもよい。
- すべてを可変にする必要はない。固定値で問題ない箇所は固定値にする。

例:

```scss
font-size: v.fluid(16, 24, 375, 1023);
padding-block: v.fluid(60, 120, 375, 1440);
```

対象になりやすいプロパティ:

- `font-size`
- `padding`
- `margin`
- `gap`
- `width`
- `height`
- `top` / `right` / `bottom` / `left`

## 6. JavaScriptルール

- JavaScriptファイルは `assets/js/` に配置する。
- サイト全体で使う共通処理は `assets/js/script.js` にまとめる。
- アニメーション専用の処理は `assets/js/animation.js` に分ける。
- JavaScriptは必要な場合だけ使う。
- HTMLとCSSだけで対応できる場合は、JavaScriptを使わない。
- 状態クラスは必要最小限にする。
- ドロワーやハンバーガーメニューの開閉状態は、基本的に `body.is-drawer-open` だけで管理する。
- `is-open`、`is-active`、`is-drawer-open` を同じ意味で混在させない。
- ボタンの開閉状態は `aria-expanded` を更新する。
- 既存コードで動いている場合は、HTML・SCSS・JavaScriptを確認してから必要な範囲だけ修正する。

---

## 7. 共通化ルール

- 同じスタイルだけを共通化する。
- 見た目や役割が違う要素を無理にまとめない。
- 同じセクション内でも、用途が違うカードやタイトルは別クラスにする。
- 片方だけ修正する可能性があるものは、共通クラスにしない。
- 迷ったら、無理に共通化しない。

---

## 8. クラス命名ルール

- BEMを基本にする。
- 状態を表す場合は、意味が重複しない状態クラスを1つ選ぶ。
- 同じ見た目でも、役割が違う要素には同じクラス名を使い回さない。
- 特定のセクション内でしか使わないクラスは、そのセクション名に合わせたBEMクラスにする。
- 共通パーツとして使わない場合は、汎用的なクラス名にしない。
- 基本定義と特定セクション内の上書きで二重指定にならないようにする。
- 例: reason内でしか使わない見出しは `.about__section-title` ではなく `.about__reason-title` のようにする。
- 既存のクラス名を大きく変更しない。

---

## 9. 修正後の確認

- Sassを変更したら、生成CSSも更新する。
- HTML・SCSS・JavaScriptの関係が崩れていないか確認する。
- 不要なクラス、不要なセレクタ、古い状態クラスが残っていないか検索する。
- 可能な場合はスマホ・タブレット・PC幅で表示確認する。
- 修正後は、変更内容と確認できたことを報告する。
- 表示確認できなかった場合は、その理由を報告する。
